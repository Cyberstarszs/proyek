Catatan Revisi & Penyempurnaan (Versi 1.1):
  - PERUBAHAN TEKNOLOGI STACK ATAS ARAHAN PENGGUNA:
    * Backend : Node.js dengan framework Express.js.
    * Frontend: Server-Side Rendering (SSR) menggunakan EJS (.ejs) + Tailwind CSS.

================================================================================
1. RINGKASAN
================================================================================

KasProyek adalah aplikasi web mandiri untuk SATU pemilik sebuah CV yang mengawasi
dana beberapa proyek pembangunan di beberapa cabang. Tiap proyek punya "kantong"
modal sendiri, misalnya Rp200.000.000. Pengeluaran (misalnya semen) dan panjar
ke pembeli material dicatat per tanggal dengan foto nota, lalu saldo proyek
berkurang. Beberapa proyek dapat berjalan di bulan yang sama tanpa uangnya
tercampur. Aplikasi memberi PERINGATAN (tidak memblokir) saat saldo minus atau
anggaran kategori terlampaui. Ada riwayat per tahun (per cabang, per proyek,
per kategori) dan proyek lama menjadi patokan biaya per m2 untuk proyek serupa.

Aplikasi dibangun menggunakan Node.js (Express.js), antarmuka template EJS (.ejs),
gaya utilitas responsif Tailwind CSS, serta basis data SQLite lokal yang ringan,
cepat, dan mudah dicadangkan.

Pembeli material TIDAK memakai aplikasi. Mereka menyerahkan nota, lalu pemilik
yang menginput.

5. ISTILAH DAN STRUKTUR DATA
================================================================================

  CV            Perusahaan milik pemilik. Hanya ada SATU CV di aplikasi (A-31).
  Cabang        Unit/kantor cabang dari CV. Wajib ada untuk mengelompokkan proyek.
                Cabang TIDAK punya saldo atau modal (A-30, A-32).
  Proyek        Satu pekerjaan pembangunan fisik. Terikat ke tepat satu cabang.
                Memegang satu "kantong" kas sendiri yang terisolasi penuh.
  Transaksi     Satu catatan mutasi uang: modal masuk, penarikan modal, belanja langsung.

  Struktur:   CV (1)  -->  Cabang (1..*)  -->  Proyek (1..*)  -->  Transaksi

  Arus Kas Tunggal per Proyek (Single-Operator Cash Model):
    Modal bersih          modal masuk dikurangi penarikan modal
    Saldo kas di tangan   uang kas riil yang tersedia fisik/rekening pemilik
    Biaya terealisasi     total pengeluaran belanja fisik riil ber-nota
    Hukum Invarian:       Saldo Kas + Biaya Terealisasi === Modal Bersih

--------------------------------------------------------------------------------
F-01  LOGIN PEMILIK (SATU AKUN)                                        [Must]
--------------------------------------------------------------------------------
Cerita: Sebagai pemilik tunggal, saya ingin masuk ke sistem secara aman agar data
keuangan CV dan proyek saya tidak dapat diakses pihak luar.
Kriteria:
  [ ] Akun pemilik dibuat melalui skrip inisialisasi awal (CLI setup/seeder Node.js).
      Tidak ada form registrasi publik dan sistem menolak pembuatan akun kedua.
  [ ] Email dan sandi cocok -> membuat sesi Express session aman dan masuk ke dasbor.
  [ ] Sandi di-hash menggunakan algoritma Bcrypt (salt rounds >= 10).
  [ ] Percobaan gagal 5 kali berturut-turut dalam 15 menit -> akun terkunci sementara
      selama 15 menit menggunakan middleware express-rate-limit. Pesan: "Email atau kata sandi tidak valid".
  [ ] Akses route data, unduhan foto, dan API tanpa sesi aktif diarahkan ke halaman login.
  [ ] Sesi login kedaluwarsa setelah 14 hari tidak aktif (disertai tombol Keluar eksplisit).
  [ ] Fitur Lupa Sandi: mengirim tautan token acak kriptografis ke email pemilik, valid 60 menit.
  [ ] Ganti sandi dari profil akun mewajibkan verifikasi sandi lama.

--------------------------------------------------------------------------------
F-02  PENGELOLAAN CV DAN CABANG                                        [Must]
--------------------------------------------------------------------------------
Cerita: Sebagai pemilik, saya ingin menetapkan identitas CV dan membuat daftar
cabang agar seluruh proyek dapat dikelompokkan dengan rapi.
Aturan terkait: BR-22, BR-24, A-30, A-31, A-32
Kriteria:
  [ ] Nama CV (tunggal, wajib, 3-100 karakter) dan logo CV opsional dapat diatur
      di menu profil perusahaan. Tampil di kop surat seluruh laporan.
  [ ] Entitas Cabang memiliki atribut: Nama Cabang (wajib, unik, 3-60 karakter),
      Kota (opsional), Catatan (opsional), dan Status (Aktif / Nonaktif).
  [ ] Nama cabang kembar (case-insensitive) ditolak oleh sistem.
  [ ] Cabang tidak dapat dihapus permanen jika sudah pernah memiliki proyek;
      cabang hanya dapat dinonaktifkan statusnya (BR-24).
  [ ] Cabang berstatus Nonaktif tidak muncul dalam pilihan dropdown proyek baru. Proyek
      lama yang berada di cabang tersebut tetap dapat diakses dan tetap masuk laporan.
  [ ] Saat pertama kali sistem dijalankan dan belum ada cabang, halaman pembuatan proyek
      memblokir input dan menampilkan panduan: "Buat minimal satu cabang terlebih dahulu".
  [ ] Cabang tidak memiliki atribut kas, saldo, atau modal. Tidak ada fitur input saldo cabang.

--------------------------------------------------------------------------------
F-03  PENGELOLAAN PROYEK                                               [Must]
--------------------------------------------------------------------------------
Cerita: Sebagai pemilik, saya ingin mendaftarkan proyek pembangunan di bawah cabang
tertentu agar aliran uang tiap proyek terpisah dan terpantau jelas.
Data Proyek: Nama Proyek (wajib, unik), Cabang (wajib, pilih satu), Jenis Bangunan
(Rumah, Ruko, Renovasi, Gedung, Lainnya), Luas Bangunan m2 (opsional, bilangan bulat > 0),
Kota/Lokasi (opsional), Tanggal Mulai (wajib), Status (Aktif, Selesai, Arsip), Catatan.
Aturan terkait: BR-13, BR-22, A-32, A-33
Kriteria:
  [ ] Proyek baru terdaftar dengan saldo kas awal Rp0 dan modal awal Rp0.
  [ ] Nama proyek kembar ditolak. Luas bangunan <= 0 ditolak. Pendaftaran proyek tanpa
      memilih cabang ditolak sistem (A-32).
  [ ] Memindahkan proyek ke cabang lain memerlukan konfirmasi dan catatan alasan pemindahan.
      Aksi perpindahan dicatat di jejak audit. Riwayat laporan tahunan selanjutnya
      menampilkan proyek pada cabang SAAT INI (BR-22, A-33).
  [ ] Perubahan status menjadi "Selesai" DITOLAK bila panjar beredar > 0 atau
      talangan belum diganti > 0. Pesan penolakan merinci nominal sisa yang belum tuntas.
  [ ] Proyek berstatus Selesai atau Arsip mengunci penambahan transaksi baru.
  [ ] Pemilik dapat mengembalikan status proyek dari Selesai/Arsip kembali ke "Aktif"
      (Re-open) dengan memasukkan alasan pembukaan kembali yang terekam di jejak audit.
  [ ] Perubahan metadata penting (jenis, luas, cabang, tanggal mulai) dicatat di jejak audit.

--------------------------------------------------------------------------------
F-04  KANTONG MODAL (MASUK, TAMBAHAN, PENARIKAN SISA)                 [Must]
--------------------------------------------------------------------------------
Cerita: Sebagai pemilik, saya ingin mencatat setoran modal awal, penambahan modal kerja,
serta penarikan sisa modal agar saldo kas mencerminkan dana nyata proyek.
Aturan terkait: BR-01, BR-02, BR-08, BR-14
Kriteria:
  [ ] Setoran Modal Masuk Awal Rp200.000.000 -> Saldo kas = Rp200.000.000,
      Modal bersih = Rp200.000.000.
  [ ] Tambahan Modal Rp50.000.000 di tengah proyek -> Saldo kas naik menjadi Rp250.000.000,
      Modal bersih naik menjadi Rp250.000.000. Riwayat membedakan modal awal vs tambahan.
  [ ] Penarikan Modal Rp40.000.000 saat saldo kas Rp40.000.000 -> Saldo kas menjadi Rp0,
      Modal bersih berkurang menjadi Rp210.000.000.
  [ ] Penarikan modal melebihi saldo kas saat itu DITOLAK: "Penarikan melebihi saldo kas proyek".
  [ ] Penarikan modal yang menyebabkan modal bersih menjadi negatif (< 0) DITOLAK.
  [ ] Nominal input <= 0 atau melebihi plafon Rp10.000.000.000 ditolak sistem (BR-01).
  [ ] Setiap form submit modal dilengkapi token idempoten untuk mencegah dobel input.

--------------------------------------------------------------------------------
F-05  ANGGARAN BIAYA PER KATEGORI                                      [Must]
--------------------------------------------------------------------------------
Cerita: Sebagai pemilik, saya ingin menetapkan pagu anggaran per kategori biaya agar
mendapatkan peringatan dini saat realisasi belanja mendekati batas rencana.
Aturan terkait: BR-10, BR-16, BR-17, A-18, A-20
Kriteria:
  [ ] Pemilik dapat mengalokasikan target anggaran untuk masing-masing kategori belanja.
  [ ] Nilai pagu anggaran per kategori dapat direvisi kapan saja dengan menyertakan alasan.
      Riwayat revisi anggaran tersimpan lengkap beserta versi sebelumnya.
  [ ] Sisa anggaran kategori dihitung otomatis: Pagu Anggaran - Realisasi Biaya Kategori.
  [ ] Total alokasi anggaran melebihi modal bersih memicu indikator peringatan warna kuning
      pada dasbor proyek tanpa memblokir pencatatan transaksi (A-18).
  [ ] Master kategori default disediakan sistem (BR-16). Pemilik dapat menambah kategori kustom.
      Kategori yang telah memiliki catatan transaksi tidak dapat dihapus, hanya dinonaktifkan.
  [ ] Anggaran bernilai negatif (< 0) ditolak.

--------------------------------------------------------------------------------
F-06  PENGELUARAN LANGSUNG                                             [Must]
--------------------------------------------------------------------------------
Cerita: Sebagai pemilik, saya ingin mencatat belanja material/jasa yang saya bayar
langsung secara tunai/transfer agar saldo kas proyek seketika terpotong.
Data Transaksi: Tanggal Transaksi, Kategori Biaya (pilih satu), Nominal (Rupiah),
Uraian Keterangan (3-200 karakter), Nama Toko/Vendor (opsional), Bukti Foto (opsional).
Aturan terkait: BR-01, BR-02, BR-09, BR-14, BR-16
Kriteria:
  [ ] Kas Rp200.000.000, belanja semen langsung Rp12.500.000 -> Saldo kas menjadi Rp187.500.000,
      Biaya terealisasi menjadi Rp12.500.000, realisasi kategori Material bertambah Rp12.500.000.
  [ ] Nominal transaksi melebihi saldo kas -> sistem menampilkan dialog konfirmasi peringatan:
      "Transaksi ini menyebabkan saldo kas menjadi minus (Rp[x]). Tetap lanjutkan?" (BR-09).
  [ ] Tanggal transaksi di masa depan (melebihi hari ini WIB) ditolak. Tanggal transaksi
      sebelum tanggal mulai proyek ditolak sistem.
  [ ] Pengiriman formulir dilindungi token idempoten: klik ganda tombol Simpan hanya
      menghasilkan tepat SATU mutasi kas tercatat di SQLite.
  [ ] Proyek berstatus Selesai atau Arsip menolak form pengeluaran langsung.

--------------------------------------------------------------------------------
F-07  PANJAR KE PEMBELI MATERIAL                                       [Must]
--------------------------------------------------------------------------------
Cerita: Sebagai pemilik, saya ingin mencatat pemberian uang muka (panjar) kepada
mandor/pembeli material agar dana yang masih dibawa mereka terpantau jelas.
Aturan terkait: BR-02, BR-04, BR-21
Kriteria:
  [ ] Panjar diberikan Rp10.000.000 -> Saldo kas berkurang Rp10.000.000, Panjar beredar bertambah
      Rp10.000.000, Biaya terealisasi TIDAK berubah (BR-04, S-A langkah 3).
  [ ] Pembeli dipilih dari daftar yang ada, atau dapat langsung mengetik nama baru secara cepat.
  [ ] Satu pembeli dapat memegang lebih dari satu panjar terbuka pada satu atau beberapa proyek.
  [ ] Panjar yang menyebabkan kas minus memunculkan konfirmasi peringatan (BR-09).
  [ ] Halaman proyek menyediakan tabel "Daftar Panjar Belum Tuntas" yang menampilkan nama pembeli,
      tanggal penyerahan, sisa panjar, dan umur panjar dalam hitungan hari.
  [ ] Tidak ada pembatasan waktu kadaluwarsa panjar; panjar tetap aktif hingga tuntas dilaporkan.

--------------------------------------------------------------------------------
F-08  NOTA PANJAR, PENGEMBALIAN SISA, DAN GANTI UANG TALANGAN          [Must]
--------------------------------------------------------------------------------
Cerita: Sebagai pemilik, saya ingin mencatat pelaporan nota belanja dari pembeli,
menerima kembali sisa uang panjar, atau mengganti uang talangan pembeli agar kewajiban tuntas.
Aturan terkait: BR-02, BR-04, BR-05, BR-06, BR-07, BR-15, A-27, A-28
Kriteria:
  [ ] NOTA MEMOTONG PANJAR: Panjar Rp10.000.000, nota pasir Rp7.300.000 dilaporkan -> Biaya
      terealisasi bertambah Rp7.300.000, Panjar beredar berkurang menjadi Rp2.700.000,
      Saldo kas tidak berubah (S-A langkah 4).
  [ ] PENGEMBALIAN SISA TUNAI: Pembeli menyetor sisa uang tunai Rp2.700.000 -> Saldo kas
      bertambah Rp2.700.000, Panjar beredar menjadi Rp0, status panjar otomatis "Lunas/Selesai".
  [ ] NOTA MELEBIHI PANJAR (TALANGAN): Sisa panjar Rp10.000.000, nota belanja Rp12.000.000 ->
      Sistem memotong penuh sisa panjar (BP = Rp10.000.000), mencatat Biaya terealisasi
      sebesar Rp12.000.000, dan otomatis membentuk kewajiban TALANGAN sebesar Rp2.000.000.
      Panjar beredar menjadi Rp0 (Lunas), Talangan belum diganti bertambah Rp2.000.000.

================================================================================
8. ATURAN BISNIS DAN SKENARIO UJI RUJUKAN
================================================================================

Seluruh formula perhitungan mengabaikan transaksi yang berstatus Dibatalkan (cancelled).

BR-01  Presisi Moneter: Semua nilai mata uang disimpan sebagai bilangan bulat 64-bit (INTEGER di SQLite,
       BigInt / Number di JavaScript). Tidak ada sen atau pecahan desimal. Nominal transaksi wajib > 0
       dan <= Rp10.000.000.000 per catatan.

BR-02  Definisi Angka & Neraca Kas Proyek:
         Modal Bersih            = MM - MT
         Saldo Kas Proyek        = MM - MT - PL - PJ + PK - GT
         Panjar Beredar          = PJ - BP - PK
         Biaya Terealisasi       = PL + NP
         Talangan Belum Diganti  = TG - GT
       Variabel Transaksi:
         MM  Modal Masuk (Awal & Tambahan)     MT  Penarikan Sisa Modal
         PL  Pengeluaran Langsung Tunai/Bank    PJ  Panjar Diberikan ke Pembeli
         NP  Nilai Nota Belanja PENUH           BP  Bagian Nota yang Tertutup Panjar
         TG  Talangan Terbentuk (NP - BP)       PK  Pengembalian Sisa Panjar Tunai
         GT  Penggantian Uang Talangan oleh Pemilik

BR-03  HUKUM INVARIAN (Keseimbangan Absolut Kas Proyek):
       Pada setiap proyek, setiap saat, rumus invarian berikut wajib bernilai BENAR:
         Saldo Kas + Panjar Beredar + Biaya Terealisasi - Talangan Belum Diganti = Modal Bersih

       Pembuktian Aljabar:
         (MM - MT - PL - PJ + PK - GT) + (PJ - BP - PK) + (PL + NP) - (TG - GT)
         = MM - MT - PL + PL - PJ + PJ + PK - PK - GT + GT + NP - BP - TG
         = (MM - MT) + (NP - BP - TG)
         Karena secara definisi TG = NP - BP, maka (NP - BP - TG) = 0.
         Hasil akhir: MM - MT (Modal Bersih). Q.E.D.

BR-04  Status Biaya Panjar: Penyerahan panjar bukan merupakan beban biaya. Beban biaya
       proyek hanya diakui pada TANGGAL NOTA sebesar nilai nota riil yang dilaporkan.

BR-05  Alokasi Nota terhadap Panjar & Nota Multi-Kategori:
       - Ketika nota belanja dilaporkan terhadap panjar terbuka:
         BP = MIN(Nilai Nota, Sisa Panjar Pembeli); TG = Nilai Nota - BP.
       - Jika nota bernilai lebih besar dari panjar, kelebihannya otomatis menjadi talangan pembeli.
       - Untuk nota multi-kategori (A-27), setiap baris kategori diproses berurutan (sekuensial):
         baris pertama memotong sisa panjar hingga habis, baris berikutnya otomatis menghasilkan talangan.
       - Sisa panjar dihitung: PJ - BP - PK (tidak pernah bernilai negatif).

BR-06  Pengembalian Sisa Panjar: Nominal pengembalian tunai wajib <= Sisa Panjar terbuka pada panjar itu.

BR-07  Penggantian Uang Talangan: Nominal penggantian kas wajib <= Sisa Talangan Belum Diganti
       pada pembeli/nota yang bersangkutan.

BR-08  Batas Penarikan Modal: Penarikan modal proyek hanya diizinkan jika nominalnya <= Saldo Kas saat itu,
       dan penarikan tersebut tidak membuat modal bersih menjadi bernilai negatif (< 0).

BR-09  Ketentuan Saldo Kas Minus: Saldo kas diperbolehkan bernilai negatif (< Rp0) akibat pengeluaran
       langsung, pemberian panjar, atau penggantian talangan mendesak, dengan kewajiban konfirmasi peringatan
       dan tampilan lencana merah pada sistem. Penarikan modal tidak boleh membuat kas minus (BR-08).

BR-10  Status Ambang Batas Anggaran Kategori:
         - Aman               : Realisasi < 80% dari Anggaran.
         - Waspada (Kuning)   : Realisasi 80% s.d. 100% dari Anggaran.
         - Melebihi (Merah)   : Realisasi > 100% dari Anggaran.

BR-11  Ketetapan Jejak Audit: Catatan transaksi tidak boleh dihapus dari basis data. Koreksi dilakukan
       melalui pembatalan berpenjelasan. Log audit bersifat append-only: waktu (WIB), alamat IP,
       data sebelum, dan data sesudah.

BR-12  Aturan Rantai Pembatalan (Cascade Protection):
         - Pembatalan transaksi PANJAR ditolak bila sudah memiliki nota belanja atau pengembalian aktif.
         - Pembatalan transaksi NOTA BELANJA ditolak bila sudah memiliki pembayaran penggantian talangan aktif.
         - Pembatalan MODAL MASUK ditolak bila menyebabkan Modal Bersih proyek menjadi < 0.
         - Pembatalan transaksi PENGGANTIAN TALANGAN (GT) diizinkan secara mandiri; efeknya mengembalikan
           kas proyek (bertambah) dan memulihkan nilai talangan pembeli yang belum lunas.
         - Pembatalan yang menyebabkan saldo kas minus diizinkan setelah melewati dialog konfirmasi (BR-09).

BR-13  Siklus Hidup Status Proyek:
         - Status Proyek terdiri dari: Aktif, Selesai, dan Arsip.
         - Perubahan status ke "Selesai" hanya valid jika Panjar Beredar = Rp0 dan Talangan Belum Diganti = Rp0.
         - Sisa saldo kas dapat ditarik terlebih dahulu menggunakan menu Penarikan Sisa Modal (F-04)
           hingga Rp0 sebelum proyek dialihkan ke status Selesai.
         - Proyek Selesai/Arsip mengunci seluruh form transaksi baru, kecuali dibuka kembali (Re-open) ke Aktif.

BR-14  Validasi Tanggal: Tanggal transaksi keuangan wajib <= Hari Ini (WIB) dan >= Tanggal Mulai Proyek.
       Waktu penyimpanan menggunakan zona waktu WIB (UTC+7).

BR-15  Konsistensi Kronologi Nota: Tanggal nota belanja dan pengembalian panjar wajib >= Tanggal penyerahan
       panjar terkait. Tanggal penggantian talangan wajib >= Tanggal nota talangan terkait.

BR-16  Struktur Kategori Belanja: Kategori awal sistem: Material, Upah Kerja, Sewa Alat, Subkontraktor,
       Transportasi, Operasional, Perizinan, dan Lain-lain. Satu baris catatan hanya untuk satu kategori.

BR-17  Ketentuan Anggaran: Anggaran kategori wajib >= Rp0. Total anggaran melampaui modal memicu peringatan kuning.

BR-18  Formula Patokan Biaya Proyek Serupa:
         Biaya per m2 = Total Biaya Realisasi Proyek / Luas Bangunan (m2).
         Syarat pembanding: Jenis bangunan sama, status Selesai, Luas > 0 m2, dari SEMUA cabang (A-34).
         Syarat aktivasi: Minimal terdapat 2 proyek selesai pembanding.
         Estimasi Proyeksi = Luas Proyek Baru x Rentang Biaya per m2 (Min, Median, Maks).

BR-19  Isolasi Saldo Proyek: Saldo uang masing-masing proyek murni berdiri sendiri (*single pocket*).
       Tidak ada mekanisme transfer uang antarproyek maupun antarcabang.

BR-20  Standar Berkas Foto Bukti: Format JPG, PNG, WebP, dan HEIC (iPhone). Maksimal 3 foto per transaksi,
       ukuran asli maksimal 10 MB per berkas. Foto HEIC wajib dikonversi otomatis menjadi JPG dan
       dikompresi di sisi browser hingga <= 1 MB sebelum pengunggahan.

BR-21  Entitas Pembeli: Data pembeli hanya berupa Nama Panggilan/Kerja. Pembeli yang memiliki riwayat
       transaksi tidak dapat dihapus, hanya dinonaktifkan.

BR-22  Peran Cabang & Mutasi Proyek: Cabang murni berfungsi sebagai pengelompokan administratif.
       Setiap proyek terikat ke tepat satu cabang. Perpindahan cabang proyek dicatat di jejak audit.
       Laporan riwayat tahunan mengelompokkan proyek berdasarkan cabang proyek SAAT INI (A-33).

BR-23  Periodesasi Laporan Tahunan: Biaya realisasi diagregasikan menurut tanggal pengeluaran langsung
       atau tanggal nota belanja; modal masuk dan penarikan diagregasikan menurut tanggal mutasinya.
       Tahun laporan mengacu pada tahun kalender masehi (WIB).

BR-24  Kekekalan Data Cabang: Cabang tidak dapat dihapus permanen jika sudah pernah menaungi proyek.
       Cabang nonaktif tidak dapat dipilih saat pembuatan proyek baru.

BR-25  Standar Pembulatan: Pembulatan pecahan matematika hanya diterapkan pada kalkulasi median patokan m2
       ke rupiah terdekat (half-up) menggunakan satu modul pembulatan terpusat di JavaScript.


SKENARIO UJI RUJUKAN (Angka Pasti untuk Pengujian Otomatis)
--------------------------------------------------------------------------------

S-A  Alur Normal Standar (Tanpa Talangan). Modal Awal Rp200.000.000.
  Langkah Transaksi                Kas (Rp)     Panjar Beredar (Rp)  Biaya (Rp)   Talangan (Rp)  Modal Bersih (Rp)
  1. Modal Masuk 200.000.000       200.000.000  0                    0            0              200.000.000
  2. Beli Semen Langsung 12.500k   187.500.000  0                    12.500.000   0              200.000.000
  3. Beri Panjar Mandor 10.000k    177.500.000  10.000.000           12.500.000   0              200.000.000
  4. Nota Pasir Lapangan 7.300k    177.500.000  2.700.000            19.800.000   0              200.000.000
  5. Mandor Setor Sisa Kas 2.700k  180.200.000  0                    19.800.000   0              200.000.000
  Uji Invarian pada setiap langkah: Kas + Panjar + Biaya - Talangan = 200.000.000. LULUS.

S-B  Alur Nota Melebihi Panjar (Terbentuk Talangan & Pelunasan). Modal Rp100.000.000.
  1. Beri Panjar Rp10.000.000 -> Kas = Rp90.000.000, Panjar Beredar = Rp10.000.000, Biaya = Rp0.
  2. Pembeli serahkan Nota Genteng Rp12.000.000 ->
     Sistem hitung: BP = Rp10.000.000 (panjar tuntas), TG = Rp2.000.000 (talangan).
     Kondisi: Biaya = Rp12.000.000, Panjar Beredar = Rp0, Talangan = Rp2.000.000, Kas = Rp90.000.000.
     Uji Invarian: 90.000.000 + 0 + 12.000.000 - 2.000.000 = 100.000.000. LULUS.
  3. Pemilik ganti talangan Rp2.000.000 -> Kas = Rp88.000.000, Talangan = Rp0.
     Uji Invarian: 88.000.000 + 0 + 12.000.000 - 0 = 100.000.000. LULUS.
  4. Upaya penggantian talangan Rp500.000 lagi ditolak sistem (talangan sudah Rp0).

S-C  Penarikan Sisa Modal dan Penutupan Proyek (Lanjutan S-A).
  Kondisi awal: Kas = Rp180.200.000, Biaya = Rp19.800.000, Panjar = 0, Talangan = 0, Modal Bersih = 200.000.000.
  1. Pemilik menarik modal Rp180.200.000 -> Saldo kas = Rp0, Modal Bersih berkurang menjadi Rp19.800.000.
     Uji Invarian: 0 + 0 + 19.800.000 - 0 = 19.800.000. LULUS.
  2. Penarikan tambahan Rp1 ditolak (melebihi saldo kas).
  3. Proyek diubah status ke "Selesai" -> Berhasil (Panjar = 0, Talangan = 0).

S-D  Rantai Pembatalan Transaksi (Cascade Cancellation & Rollback).
  Mengacu kondisi S-A langkah 4 (Kas: 177.500.000, Panjar: 2.700.000, Biaya: 19.800.000, Modal: 200.000.000):
  1. Batalkan transaksi panjar Rp10.000.000 -> DITOLAK (karena ada nota pasir aktif).
  2. Batalkan transaksi nota pasir Rp7.300.000 -> BERHASIL.
     Panjar beredar kembali menjadi Rp10.000.000, Biaya kembali menjadi Rp12.500.000.
  3. Batalkan transaksi panjar Rp10.000.000 -> BERHASIL.
     Saldo kas kembali menjadi Rp187.500.000, Panjar beredar kembali menjadi Rp0.
  4. Pengulangan pembatalan pada transaksi yang sama tidak merubah saldo (idempoten).

S-E  Agregasi Riwayat Tahunan Multi-Cabang.
  Cabang 1: Rumah A, Ruko B.   Cabang 2: Renovasi C.
  Tahun   Cabang 1                              Cabang 2     Total
  2025    90.000.000 (Ruko B)                   0            90.000.000
  2026    78.300.000 (Rumah A 19.800.000        41.800.000   120.100.000
                      + Ruko B 58.500.000)
  Total realisasi Ruko B lintas tahun = Rp148.500.000 (Rp90.000.000 + Rp58.500.000).

S-F  Ambang Batas Peringatan Anggaran (Pagu Material: Rp80.000.000).

9. KEBUTUHAN NON-FUNGSIONAL
================================================================================

  Arsitektur & Tumpukan Teknologi (Tech Stack)
    - Runtime  : Node.js (v20+ LTS).
    - Framework: Express.js (ringan, cepat, fleksibel).
    - Template : EJS (.ejs) untuk Server-Side Rendering (SSR) yang terintegrasi Tailwind CSS.
    - Database : SQLite (menggunakan driver performa tinggi `better-sqlite3` atau `sqlite3`).

  Performa & Responsivitas
    - Waktu respon server (TTFB) <= 100 ms untuk seluruh render halaman.
    - Waktu muat halaman penuh di jaringan seluler 4G lapangan <= 2 detik.
    - Beban aplikasi sangat rendah (1 pengguna pemilik aktif).

  Integritas Moneter & Konkurensi SQLite
    - Database SQLite dikonfigurasikan dengan mode WAL (`PRAGMA journal_mode = WAL;`)
      dan `PRAGMA busy_timeout = 5000;`. Mode ini memungkinkan operasi baca (read) berjalan
      bersamaan tanpa memblokir operasi tulis (write).
    - Seluruh operasi mutasi saldo kas proyek dibungkus dalam transaksi atomik terisolasi:
      `BEGIN IMMEDIATE TRANSACTION ... COMMIT` untuk mencegah race condition.
    - Setiap submit form mutasi uang menyertakan Idempotency Key (UUID) yang divalidasi
      oleh Express middleware untuk meniadakan risiko duplikasi mutasi akibat klik berulang.
    - Tipe data nominal moneter menggunakan `INTEGER` 64-bit di SQLite (bebas floating point error).

  Penanganan Media & Penyimpanan
    - Kompresi foto dan konversi format HEIC (iPhone) dilakukan di sisi peramban web (*client-side*
      menggunakan HTML5 Canvas / JS) sebelum transmisi jaringan ke endpoint upload Express.
    - Estimasi file database SQLite hanya sekitar 10-50 MB per 5 tahun penggunaan intensif.
    - Berkas foto disimpan di folder privat `data/uploads/` yang dilindungi oleh Express middleware.

  Keamanan & Jejak Audit
    - Proteksi CSRF pada seluruh route mutasi data EJS form.
    - Keamanan sesi menggunakan cookie bertanda `HttpOnly`, `SameSite=Strict`.
    - Rate limiting pada endpoint login menggunakan `express-rate-limit` (maksimal 5 percobaan per 15 menit).
    - Sanitasi output teks terhadap potensi serangan XSS dan injeksi formula spreadsheet (`=`, `+`, `-`, `@`).

  Keandalan Operasional Lapangan
    - Antarmuka web responsif dioptimalkan untuk layar smartphone pekerja/pemilik di lapangan.
    - Kontras elemen tinggi dan ukuran tombol sentuh minimal 44 x 44 piksel agar nyaman
      digunakan di bawah terik sinar matahari.
    - Penanganan gagal unggah foto yang anggun: mutasi angka tetap tersimpan aman di SQLite,
      disusul status visual "Upload Foto Tertunda / Coba Lagi".

  Bahasa, Mata Uang, & Waktu
    - Antarmuka sepenuhnya berbahasa Indonesia.
    - Satuan moneter: Rupiah (IDR).
    - Penanda waktu: Waktu Indonesia Barat (WIB / UTC+7).
